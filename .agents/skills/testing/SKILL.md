# Testing

## The harness

`tests/check.hpp` is the whole framework. `TEST(name) { … }` registers a case.
`CHECK(cond)` records a failure and carries on. `CHECK_BITS(got, want)` compares two
doubles by bit pattern and prints both values in hex. `tests/main.cpp` runs every case
and prints `ok` or `FAIL` per test.

- One file per topic: `tests/<topic>_test.cpp`, with a `ge:` tag block like every source
  file (the `write-code` skill, § Discovery tags); the module it tests names it in `ge:test`. `tests/CMakeLists.txt` globs
  `*_test.cpp`, and each file becomes its own executable and CTest case, so nothing is
  registered by hand.
- `ge::test::root_path("tests/golden/x.txt")` opens files relative to the repo.
- `tests/golden.hpp`: `golden_rows(path)` returns rows of `uint64_t` hex words, and
  `as_double(u)` reinterprets them. A codec's strings (the tape's base64) go in a text file
  read with `golden_words(path)`, with arbitrary text hex-encoded (`unhex`).

## Golden files

- They are the engine's own record of its bits, not a reference to match. A table first
  comes from a generator (`make golden`; while porting those live in `porting/parity/`)
  or from the engine's own output once the behaviour is reviewed, never typed by hand.
- Format: one row per line, whitespace-separated hex (`%016llx` doubles, plain hex
  integers). Inputs come first, then outputs. A leading `#` line may carry
  provenance (the generator's environment). Booleans are `0`/`1` doubles; an optional is the pair
  `has value` (`0 0` when absent). A module with no numbers (`core/output`) gets a text
  transcript the C++ test reproduces by running the same script.
- Anything that reaches a transcendental is generated by `make golden-libm`, on the one
  platform whose bits the tables pin.
- Committed. A deliberate change of behaviour rewrites the tables it moves in the same PR,
  and the PR says why the values moved and shows the behaviour is still right (a map still
  builds clean, a run still finishes). An unexplained move is a bug.
- A table the engine writes itself has a `GE_GOLDEN_WRITE` branch in its test (set, the test
  writes its file instead of comparing). `make ge ARGS="golden write <topic>_test"` runs it on
  the release build, runs it again to hold it, and answers with what moved;
  `make ge ARGS="golden diff --base=origin/main"` is the same table for every golden file the
  branch changed: each column that moved, in how many rows, and the rows (a double's bits shown
  as the double). Paste that into the PR's why. A digest written beside its PARTS word
  (`name:hex,name:hex,...`, Fall Line's `state_parts` after `state_hash`) is diffed a part at a
  time: `parts.army moved in 5 rows` says which part moved, so a digest another PR's system moved
  is told from a cross-platform break. A new golden row with a state digest writes its parts too.
- Keep a file under about 1 MB. Draw inputs from a fixed mulberry32 seed so the table
  is reproducible.

## What a test owes

- A simulation module: bit equality with a golden table covering every branch.
- A behaviour that matters (an invariant, a rule): an assertion of it.
- A bug fix: the failing case first.

## Running

```sh
make test                                   # everything, debug + sanitizers
ctest --preset debug -R core_math           # one topic
./build/debug/tests/core_math_test          # direct, with full output
```

Slow tests (a full level build, a simulated run) are fine, but keep each executable
under about 30 s in debug so the CI matrix stays quick.

## Labs are tests too

CTest's `labs_smoke` runs every lab at its smoke flags twice in one process and checks each
digest against `tests/digests/` (the `labs` skill). A behaviour worth LOOKING at gets
a lab. A behaviour with one right answer gets a test. Many subjects need both, and a
scenario row (M5) can back both at once.
