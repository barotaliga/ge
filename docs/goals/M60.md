Status: open
Milestone: **Shooter seams: shared layers and per-game modules**
Exit: Every piece more than one classic game uses lives in `plugins/shooter` or the engine, each classic game's own code sits behind one module table that remix and any later shooter game load, and nothing shared asks which game is running
Labs: `se-net`, `se-sequel-net`, `se-interop`

Asked by the maintainer on 2026-11-14: the engine holds the broad services every game shares
(accounts, the hub, proxy, forward, TV, the dedicated server, the guards); `plugins/shooter` holds
everything a shooter game shares (formats, the protocol family, the rules runner's seam, bots,
movers, remix's machinery); each classic game's own code is a thin module that remix can load into
another shooter game. A third classic game, a fourth and a game of another family (a grid-map
shooter) are kept room for and not built. The survey behind the plan, with its diagram:
https://claude.ai/artifact/NwWyMmGUsJK4HWbBxGqjtj.

The survey's findings, in the order of their pull requests:

- **M60a (done, #959): the protocol family.** The net channel, the info strings and the wire's fields,
  quantization and CRC-16, which the first game's protocol and the sequel's share, move from
  `games/shooters_edge/net/classic_*` to `plugins/shooter/protocol/` (`channel.hpp`, `info.hpp`,
  `wire.hpp`); `net/protocol.hpp` names them in the game's net namespace. Each game's own protocol
  keeps its version, ports, move checksum and usercmd (`net/classic_wire.hpp`). No behaviour
  changes: the quantize golden moves with the code (`tests/golden/shooter_protocol_quantize.txt`)
  and every other golden and digest is unchanged.
- **M60b: the content layer.** The game adapter's table, the search path and the shared open
  calls (models, skins, textures, sounds, pictures) into `plugins/shooter/content/`, so any shooter
  game opens any classic game's files through one call.
  - **M60b1 (this PR): the search path.** `client/files` and `client/load_order` (the install's
    folders, packs, zips and loose files in each game's own order, saves, the palette, a map's
    light, sky boxes, the release's words by key) move to `plugins/shooter/content/` as
    `ge::shooter::content`; the bundled client's folder becomes load-order data
    (`LoadOrder::client_folder`, its name) with `client_folder()` beside the search path. The
    client keeps its names through two headers of using-declarations, so no caller changes.
    Next: the adapter's shared open calls (`client/adapter_parts`: models, sounds, textures,
    configs, place names, demos).
- **M60c: the player CLI's groups.** The modder's commands `ge` has and the game CLI lacks (pak,
  qc, mod check and pack, cfg check and dump, the map tools, content scan) become row groups on the
  game CLI's frame (`engine/gamecli/`, `plugins/<name>/cli/`), which `ge` calls too: one body,
  two front doors. The two copies of demo pack and unpack become one.
  - **M60c1 (done, #964): the toolkit and its first group, `pak`.** `engine/toolkit/` (`ge::toolkit`)
    holds the shared bodies as rows run with a `Call` under the program's own name; `ge` and every
    `<game>_cli` list and run them (`secli pak ls|extract|build|convert|sum`). The answer shape
    (`Outcome`, `Finding`) moves there from `engine/cli`. Next: `qc`, `mod`, `cfg`, the map tools,
    the demos.
  - **M60c2 (done, #988): the `qc` group.** The five `qc` rows move to `engine/toolkit/qc.hpp`, with
    the one reader of the tool's answer. A row names the tool its body is (`Row::tool`); `ge` builds
    the repo's `progs` executable for it, `secli` runs the progs plugin's tool in its own process
    (`plugins/progs/cli/`), and the tool's next steps name the program that called it.
  - **M60c3 (done, #996): the `mod` group.** `mod check`, `pack`, `key` and `sign` move to
    `engine/toolkit/mod.hpp` with the table of games that offer mods; `ge` keeps `mod new`, `mod
    build` and `mod check --run`. A row may need something of the game (`Row::needs`), and a CLI
    lists it only when its `Spec::offers` names it (`Spec::tools` is renamed `offers`).
  - **M60c4 (this PR): the `map` group.** `map info`, `ents`, `liquids`, `slice` and `check` (the
    brush plugin's tool, until now only `ge tool brush -- ...`) become toolkit rows in
    `engine/toolkit/map.hpp`: `ge map ...` builds the repo's `brush` executable, `secli map ...`
    runs the tool in its own process (`plugins/brush/cli/`), beside the plugin's `map build` and
    `map plan`. The settings needed no move: both doors check and tidy a cfg through
    `engine/console/cfg.hpp` (`ge cfg` runs the game's console, `secli settings check|format` the
    player's files). Nor did the demos: `ge demo pack` wraps any recording in zstd and `secli
    demos pack` writes the game's replay file, two jobs over the one reader (`vfs::unpack_one`).
    `content scan` stays `ge`'s: it builds a game's asset map in its repository. M60c is done.
- **M60d: the rules runner's calls.** Each place shared code asks `sequel_of(rules)` or
  `qc_of(rules)` (about 50) becomes a call on `RunnerCalls`.
  - **M60d1 (this PR): shots and screens.** A shot in flight is named in its row of the rules'
    world (`WorldEntity::shot`: rocket, grenade, nail, bolt, ball), by class for a program and by
    kind for the sequel's own rules, so the window's trails, lights and blasts read one list
    whatever runs the rules. Two traits on `RunnerCalls` say what a game's rules do for the window:
    `own_screens` (they draw their own scoreboard and inventory) and `own_words` (they answer the
    console's unknown lines). Three `sequel_of` and two `qc_of` reads in the client go. Next: the
    held weapon, the speed jump's air law, the HUD's numbers and the recorder's format.
- **M60e: bots off the server's types**, then `games/shooters_edge/bots` into `plugins/shooter`.
- **M60f: item roles.** Remix's pairwise item rows become one table a game, each game's items to
  shared roles (with the remix thread, M18u).
- **M60g: the game module table**, the sequel's files behind it in a library of their own, then
  the first game's.
- **M60h: the movers kit and the monster kit**, one shared state machine each with every game's
  numbers as data, goldens on both games.
