Status: open
Milestone: **Classic game profiles**: Shooter's Edge as a shell that loads the classic games the player owns, each a profile (its game directories and packs, its formats, its default program and movement, its content rules) chosen independently of the program, the movement and the arsenal (weapons and armour, each swappable on its own), so games can be mixed; the classic game's profile first, its sequel's (BSP 38, its models, its rules as a C++ mod written clean-room, its own move) the second, the third's later
Exit: The classic game's profile in data with no game name in the shell or the loop; a second profile loaded from the sequel's demo pack showing a map in the window; a remix (one profile's map with another's movement) played by a bot with a golden digest; the classic campaign's first map played on our campaign variant with the sequel's weapons and, separately, its armour
Labs: `se-profiles`, `bsp`, `pak`

The design is `docs/shooters-edge.md` § Profiles. Steps:

- **M18t1, the profile row**, in two halves. The CONTENT half (where the files are and what
  kind each is) is `plugins/classicenhance/profile.hpp`'s `kProfiles`, shared by classic-enhance
  and the game: **landed** for classic-enhance (every stage finds its files through
  `Source::profile`; the first game's digests unchanged). (a) **Landed** for the client and its labs:
  `client/files.hpp` is `engine/vfs`'s search path over the profile's base folder with a mod
  folder (`-game`) mounted over it, pk3s read too, and classic-enhance's cache found by every
  base pack (the full game's cache was missed); the dedicated server's folder comes with (c).
  (b) **Landed** for the renderer and the light bake: the map readers mark sky, liquids (with
  teleports) and animation in the map view (`brush::Texture`'s `sky`, `liquid` and `next`), and
  nothing past the reader reads a name; classic-enhance's own material rule by name
  (`texture.cpp`) is still to move. (c) **Landed** for the window: `games/shooters_edge/profiles/game_profile.hpp`'s rows give
  each mode's program files (`qwprogs.dat`, then `progs.dat`, for multiplayer) and the
  fallback map, and the window takes its start map, its full-game rule and the base folder's
  name from the content row; still to come, the dedicated server reading files through the
  search path (its `base_dir` is held equal to the content row's by a test) and the default
  movement. Then, in order: (c) the rest of the GAME half
  (the default movement, the dedicated server's files, the menu's map list) read by the window,
  the menu and the server; (d) the item and weapon names the bots,
  HUD and arsenal know (with the team bots' table, `games/shooters_edge/bots/`).
- **M18t2, research for the sequel**: a clean-room note set (`porting/shooters-edge/` or its
  own working directory) for its packs, maps, models, game rules and move, by a research session.
- **M18t3, the sequel's content**: its maps (already read by `plugins/brush`) and models drawn.
- **M18t4, the sequel's rules** as a C++ mod on `engine/mod`, and its move as a third
  `sv_playermove` value.
- **M18t5, remixes**: any profile's content with any program and movement the content can carry,
  checked at load (a program's precaches must resolve in the content).
- **M18t6, the arsenal**: weapons and armour as data rows per profile (models, sounds, icon, ammo,
  fire, damage; armour's absorption), `qc/common/` reading them, `sv_weapons` and `sv_armour`
  choosing a set each, a map's item names mapped to slots so another set fills them, and the
  load check naming a missing pack (`docs/shooters-edge.md` § Weapons and armour). The data shape
  lands with our campaign variant (M18s) so nothing there hard-codes a weapon.
