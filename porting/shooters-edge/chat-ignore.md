Words used below:
- "Scoreboard name" is the player's name as the client keeps it for display.
- "Userinfo name" is the raw name value the server sends in the player's info string.
- "Slot" is the player's scoreboard position (0 to 31).
- A chat line is "categorized" by the client before any ignore rule runs (see question 2).

## 1. `ignore <name or id>`

Name or id [read]:
- The client first tries the argument as a user id, but only when every character is a digit. If a player has that user id, that player is the target.
- Otherwise it tries names, in this order, and the first player that matches wins:
  1. the whole argument equal to the scoreboard name, case-sensitive,
  2. the same, ignoring case,
  3. the same against the name with colours and high-bit characters folded to plain ASCII (each character mapped to its readable form, top bit cleared), ignoring case.
- [derived] All three name steps compare the whole name, including its end. So "bob" does not match "bobby" (no partial or prefix match at these steps).
- [read] If all three fail, the argument is used as a regular expression (PCRE2, case-insensitive, not anchored) against each colour-stripped name, and the first player whose name contains a match is chosen.
- [derived] So "ignore bo" ends up taking the first player (lowest slot) whose plain name contains "bo". A pattern that does not compile matches no one. Regex special characters in a typed name take effect.
- [read] Last, a digits-only argument is tried as a user id again.

What is stored [read]:
- One flag on the player's slot. Neither the name nor the user id is kept anywhere else.
- When the voice chat build option is on, the same command also sets a separate voice-ignore flag on that slot.
- The list shown by `ignorelist` is simply every occupied slot whose flag is set.

Reconnects and renames:
- [read] A rename keeps the ignore, because the flag stays on the slot when the info string changes.
- [read] When an empty slot is taken by a newly joined player, the flag is cleared. A player who leaves and rejoins is therefore no longer ignored.
- [read] The whole client state, including every flag, is wiped when a new server data message arrives (every map change and every connect). [derived] The player ignore list does not survive a map change.
- [read] Leaving a slot does nothing. The flag is cleared only when the slot is next filled.

Limits [read]:
- One flag per slot: 32 slots, so up to 32 players.
- Nothing stops you ignoring yourself. Your own team messages generated by the teamplay message functions are then skipped.

Messages, where `<cmd>` is the command as typed (`ignore`, `unignore` and so on) [read]:
- Success: "Added user <name> to ignore list", where <name> is the scoreboard name.
- Already ignored: "User <name> is already ignored".
- No player found: "<cmd> : no player with userid <n>". Here <n> is the argument read as a number: 0 for a name, or the leading digits of the argument.
  - [derived] An unknown NAME therefore also prints the userid wording, for example "ignore : no player with userid 0".
  - [read] Only an empty argument (a quoted empty string) gives "<cmd> : no player with name <arg>".
- Wrong number of arguments: "Usage: <cmd> [userid | name]".
- No argument at all: prints the whole list, the same as `ignorelist`.

`ignore_id <n>` [read]:
- Accepts only digits; anything else prints "Usage: <cmd> [userid]".
- Looks up the user id only, with the same success, already-ignored and no-player lines as `ignore`.

`unignore` and `unignore_id` [read]:
- Find the player the same way as `ignore` and `ignore_id`.
- Print "Removed user <name> from ignore list" or "User <name> is not being ignored".
- [read] `unignore` also clears the voice ignore on that slot.

`ignorelist` [read]:
- With any argument it prints "<cmd> : no arguments expected".
- Otherwise it prints, in order:
  1. A highlighted header "User Ignore List:", then the ignored players' scoreboard names, laid out in padded columns across the console line.
  2. (Voice build only) "VOIP Ignore List:" and the players who are voice-ignored but not text-ignored.
  3. "Team Ignore List:" and the team names.
  4. "Opponents are Ignored" when ignore_opponents is not 0.
  5. "Spectators are Ignored" when ignore_spec is 2, or when it is 1 and you are not a spectator.
  6. "Qizmo spectators are Ignored" when ignore_qizmo_spec is on.
  7. "QuakeTV observers are Ignored" when ignore_qtv is on.
  8. A blank line.
- Each header is shown even when its list is empty.

## 2. Which incoming lines are dropped, and how the speaker is found

Only server prints at chat level are tested [read]:
- The rules run on lines the server sent at the chat print level.
- The weapon and ammo filters run at the high print level (question 7).

How a chat line is categorized [read]. For each occupied slot, the client takes the userinfo name,
cut to 31 characters, and checks the line's start:
- "<name>: " is open chat: "normal", or "spectator chat" if that player is a spectator.
- "(<name>): " is team chat. It is marked as team chat only in these cases:
  - you are a player, or you are a spectator tracking someone; and
  - the speaker is you, or teamplay is on and the speaker's team equals your team (or, when you spectate, the tracked player's team). Otherwise the line is left without a type.
- "[SPEC] <name>: " is spectator team chat. It counts only when you are a spectator and the speaker is a spectator.
- The marks from every player that matches are combined.
  - [derived] When two names both match the start of a line, the line carries more than one type. No player-based ignore rule then applies to it (each rule expects exactly one type), though the spectator and QTV rules below can still drop it.
- QuakeTV chat, which is recognised by a "#<digits>:" proxy prefix in the raw text and rewritten with the QTV chat prefix setting, carries an extra "QTV" mark.

Finding the speaker [read]:
- The name is cut from the line by position: the characters before ": " (or inside the brackets, or after "[SPEC] "), at most 31 characters.
- That name is then looked up against the userinfo names: exact and case-sensitive, on the first 31 characters, with no colour folding.
- The first slot that matches is the speaker.
- No server print level or sender id is used. Only the text and the scoreboard are.
- [derived] Two players with the same name, or a name that is a prefix of another before ": ", can be confused.

What an ignored player loses [read]:
- Open chat is dropped.
- Team chat is dropped only when ignore_mode is 1. With ignore_mode 0 (the default), every line marked as team chat skips all the ignore rules in question 2, including the user list.
- Spectator open chat and spectator team chat are dropped. The ignore_mode exemption covers only the team-chat mark, not spectator team chat.
- Private messages are not a separate category in this client. A line that does not start with a known "<name>: " form gets no type and is never dropped by the user list.
- Voice: `ignore` also mutes the player's voice (voice build only).
  - [read] `unignoreall` clears the text flags only, so voice mutes stay.
  - [read] The separate commands `ignore_voip <userid | name>` and `unignore_voip` toggle the voice mute alone. Their messages are "Added/Removed user <name> to/from ignore list" and "User <name> is already/not ignored".

Order and side effects [read]. The client works through a chat line in this order:
1. The teamplay suppress hook.
2. The checks for f_ requests (version and similar queries). [derived] These are still answered for an ignored player.
3. The ignore rules (user list, spectators, QTV, opponents, teams).
4. The Qizmo spectator check.
5. The flood check.

A dropped line:
- [read] goes nowhere: not to the console, not to the chat sound, not to the message triggers (triggers run only on lines that reach the console), and so not to the console log,
- [read] is echoed only as a developer debug line, beginning "Ignoring message:", "Ignoring qizmo message:" or "Ignoring flood message:", shown only with developer mode on.

## 3. `ignore_team <team>`

Adding [read]:
- The argument must equal, exactly and case-sensitively, the team of at least one occupied, non-spectator slot right now. Otherwise the client prints "<cmd> : no team with name <team>".
- Already listed: "Team <team> is already ignored". The check compares the first 16 characters.
- Added: "Added team <team> to ignore list". The name is stored cut to 16 characters.
- The list holds 4 teams.
  - [read] When it is full, the client prints "You cannot ignore more than 4 teams" but does not stop there: it goes on to write a fifth entry past the end of the list and prints the "Added" line too.
  - [derived] That is a defect (it writes out of bounds), not a designed limit, and the result is undefined.

Removing [read]:
- `unignore_team <team>` matches on the first 16 characters and fills the hole with the last entry, so the order changes.
- It prints "Removed team <team> from ignore list" or "Team <team> is not being ignored".
- `unignoreall_team` clears the list and prints "Team ignore list cleared".
- With arguments it prints "<cmd> : no arguments expected".
- Without an argument, `ignore_team` and `unignore_team` print the list. With too many arguments they print "Usage: <cmd> [team]".

Live, not stored per player [read]:
- On each chat line, the speaker's CURRENT scoreboard team is compared with each listed team (first 16 characters, case-sensitive).
- A player who changes team is judged by the new team at once.

When the team list applies [read]:
- Only with teamplay on (the server's teamplay value not 0).
- Never to a spectator speaker.
- Never to a line whose speaker name equals your own name.

Lifetime:
- [read] The team list is kept outside the per-map state.
- [derived] It survives map changes and reconnects until the client quits.

## 4. `ignore_opponents` 1 and 2

The line must meet all of these [read]:
- It is plain open chat from a player (the "normal" type only). So team chat, spectator chat and QTV chat are never dropped by this setting.
- You are not a spectator.
- The speaker is not your own slot.
- Either teamplay is off, or the speaker's team differs from yours.
  - [derived] With teamplay off, every other player is an opponent.

When it applies [read]:
- Value 1 (menu "always") applies whenever those conditions hold.
- Value 2 (menu "on match") applies only while all of these hold:
  - you are connected,
  - not playing a demo,
  - not a spectator,
  - the server info key "status" is not "standby" (compared ignoring case).
  - [derived] A countdown, or a server that does not set "status", counts as "during a match".
- Any other non-zero value behaves like 2. [derived]

## 5. `ignore_spec` 1 and 2

What counts as spectator chat [read]:
- Open chat ("<name>: ") whose speaker is in a spectator slot on the scoreboard.
- "[SPEC] <name>: " lines, recognised only while you are a spectator yourself.
- The server's "[SPEC] " prefix matters only for that second form. For open chat the scoreboard's spectator flag decides.

Values [read]:
- 2 drops both kinds.
- 1 drops spectator OPEN chat only, and only while you are not a spectator.
  - "Unless you spectate" means: when your own client is a spectator, the setting does nothing.
  - "[SPEC]" team lines are never dropped by 1.
- The menu names the values "off", "on (as player)" and "on (always)".

The related settings [read]:
- `ignore_qtv` (non-zero) drops any chat line carrying the QTV mark.
- `ignore_qizmo_spec` (non-zero) drops a chat-level line that has no type, starts with "[" and contains "]: ".

## 6. `ignore_flood` and `ignore_flood_duration`

Which lines are checked [read]:
- Value 1 (menu "say/spec") checks open chat and spectator open chat.
- Value 2 (menu "say/say_team/spec") also checks team chat and "[SPEC]" team chat.
- Lines with no type are never checked.
- Lines whose speaker name equals your own name are never checked, except during demo playback.

What "repeated" means [read]:
- The client keeps the last 10 lines that passed the check, from any players, in a ring.
- A new line is dropped when an EARLIER line in that ring has exactly the same full text, including the "name: " prefix and compared on up to 2047 characters, and that earlier line was kept less than ignore_flood_duration seconds ago (real time).
- [derived] It is the same text from the same name, not any line from the same player. Different text from the same player always passes.

Which line is kept, and the timing [read]:
- The first line is kept and recorded.
- A dropped repeat is NOT recorded.
- [derived] So the window runs from the first (kept) occurrence, not the last. A player repeating a line every second with the duration at 4 shows it at 0 s, 4 s, 8 s and so on.
- [derived] Only the 10 most recent kept lines are remembered, so busy chat can push the original out early.

Defaults and reset:
- [read] The ring is cleared on every new map.
- [read] ignore_flood_duration defaults to 4 seconds. The menu offers 0 to 10 in steps of 1.
- [derived] 0 disables the dropping.

Order [read]:
- The flood check runs after the ignore rules, so lines already dropped by an ignore are never recorded.

## 7. `ignore_no_weapon` and `ignore_not_enough_ammo`

[read]
- These test lines the server prints at the HIGH print level, not chat.
- With `ignore_no_weapon` above 0, a line whose text BEGINS with "no weapon" (lower case, prefix match) is dropped.
- With `ignore_not_enough_ammo` above 0, a line that begins with "not enough ammo" is dropped.
- Dropped lines are not shown and do not reach the triggers.

[derived] The words the server actually sends, such as "no weapon.", are the server's own text.
The client tests only those starting words.

## 8. Saving, and silence

Saving:
- [read] The ignore settings (ignore_flood, ignore_flood_duration, ignore_spec, ignore_qizmo_spec, ignore_qtv, ignore_mode, ignore_opponents, ignore_no_weapon, ignore_not_enough_ammo) are ordinary settings in the "Chat Settings" group. `cfg_save` writes them like any other setting: only the ones changed from their default, unless cfg_save_unchanged is 1.
- [read] The player list and the team list are not written by the config writer.
- [derived] They are lost on quit. The player list is also lost on each map change (question 1).

Not silent [read]:
- `unignoreall` prints "User ignore list cleared".
- `unignoreall_team` prints "Team ignore list cleared".
- With an argument, each prints "<cmd> : no arguments expected" and does nothing.
- [read] The command names are registered as "unignoreAll" and "unignoreAll_team". [read] Console command lookup in this client ignores case, so typing them in lower case works.
